# House Bot over the real protocol, with a one-answer cheating mode (v1 review)

A new `apps/house-bot` package (`@accident/house-bot`) adds a Node House Bot that plays Accident through the real `@accident/protocol` `Session` rather than reimplementing any of the handshake, play gate, auto-answer or reveal (REQ-17.1). To support the cheating demonstration (REQ-17.2 / REQ-18.3), the shared `Session` grew one additive `answerPolicy` hook: honest by default, and when supplied it overrides only the ANSWER feedback while the encoder still enforces validity. The bot wires that into a `cheat: { atGuessIndex }` option that lies on exactly one of its own answers with a valid-but-wrong `Feedback`, which the unchanged finalisation path then charges as a `wrong-answer` fault. Bot labelling (REQ-17.3) is a bot-layer badge (`HOUSE_BOT_LABEL`, `label`, `marker()`) that pairs the label with the seat's public key without touching protocol validation.

Watch for: the `Session` seam is genuinely additive and backward-compatible — verified the honest path is byte-for-byte unchanged when no policy is passed (**confirmed**). The cheating test drives the real `finalise.ts` lie detection, which is untouched by this diff, so the demonstration exercises production logic rather than a test-only stub (**confirmed**). No blocking concerns found.

**Verdict**: APPROVED

## High-level view

The bot owns a single `Session` and does one thing on top of it: when the view says it may guess, it rebuilds its own answered turns, narrows candidates with the engine's `candidatesFromHistory`, and calls `chooseGuess` — the exact algorithm the protocol harness's `autoplay` uses. Everything else (commit, the on-chain play gate, honest auto-answering, reveal, finalisation) stays inside the Session, so REQ-17.1's "same code paths as the Client" holds in substance, not just in name.

The cheating mode is a thin policy over the new Session seam. The seam adds an optional `answerPolicy` to `SessionConfig`, threads it through `create()`/constructor, and consults it in `step()` only after computing the honest score; with no policy the honest score is sent exactly as before. The bot's policy lies on one configured index by returning the first valid feedback that differs from the truth, keeping every other answer honest. Because finalisation re-scores each answer against the revealed secret, the single lie surfaces as a `wrong-answer` fault and the honest seat wins by `fault` — the real detection path, not a shortcut.

Labelling lives at the bot layer deliberately: the relay HELLO payload is fixed to `host | guest`, so the badge is a `marker()` tying `HOUSE_BOT_LABEL` to the seat's public key. This satisfies REQ-17.3 without weakening message validation, but it is only a surfaced capability — nothing in this diff renders or consumes the marker in a room UI, which is expected since the web client is out of scope here.

Live operation (`src/live.ts`) is isolated: it reads config from env, builds a real `SolanaChain`, and does no I/O at import time. It is never imported by tests and is excluded from the coverage bar, as is the re-export barrel.

### The `answerPolicy` seam is additive and leaves honest play untouched

The only change to shared code is in `packages/protocol/src/session.ts`. `AnswerPolicy` is a new optional field on `SessionConfig`, carried through `create()` into the constructor and stored as `private readonly answerPolicy`. In `step()`, the ANSWER branch now computes the honest `score(s.secret, guess)` as before and sends it verbatim unless a policy is present:

```ts
const honest = score(s.secret, guess);
const feedback = this.answerPolicy
  ? this.answerPolicy({ index, guess, secret: s.secret, honest })
  : honest;
await this.sendBody({ type: 'ANSWER', index, feedback });
```

With `answerPolicy` undefined the computed `feedback` is identically `honest`, and the ANSWER encoder still runs `isValidFeedback` on whatever a policy returns, so a policy cannot inject feedback 31 or an impossible dead+injured combination — the seam can only substitute one of the 14 valid feedbacks, never weaken validation. The honest-default half of `session.seam.test.ts` asserts an empty fault list and verdict agreement, so a regression that accidentally consulted a policy on the honest path would fail there. The full protocol suite (387 tests) passes unchanged, the strongest evidence the seam is non-invasive.

### The cheating mode exercises the real finalisation lie-detection path

`cheatingPolicy` returns, for the targeted index, `VALID_FEEDBACK.find((v) => v !== honest)` — the first of the 14 valid feedbacks that differs from the true score — and `honest` everywhere else. That guarantees a syntactically valid ANSWER that is provably wrong. The important property for REQ-18.3 is that detection is not reimplemented in the bot: `finalise.ts` (unchanged in this diff) re-scores every answer against the seat's revealed secret via `findLies` and pushes a `wrong-answer` fault with `claimed` and `actual`. The cheating test asserts `verdict.reason === 'fault'`, `result === 'seat1'`, the fault's `seat`/`index`, `claimed !== actual`, and that `actual === score('1964', guesses[1])`. If the finalisation lie logic were reverted, that assertion chain would fail — the test is anchored to the real detector, not to the bot's own claim.

The mirrored assertions in `session.seam.test.ts` prove the same at the protocol layer with a hand-written policy, so the behaviour is pinned both where the seam lives and where the bot consumes it.

### Guess selection reuses the proven autoplay, honouring "same code paths"

`chooseHonestGuess` filters the view's guesses to the bot's own answered turns (`index % 2 === view.seat && answers[index] !== undefined`), feeds them through `candidatesFromHistory`, and calls `chooseGuess(level, …, rng) ?? OPENING_GUESS`. This is line-for-line the algorithm in the protocol harness's `autoplay` (visible in `session.seam.test.ts`), so the bot is not a second, divergent implementation of play. The `?? OPENING_GUESS` fallback is deliberate and tested: when an opponent's lie makes the answers mutually inconsistent, no candidate survives, and rather than stall the bot replays a valid code so the game can still reach finalisation where the lie is caught. The `chooseHonestGuess` unit tests cover the opening, the narrowing, and the inconsistent-answers fallback.

### Submission guarding and background-error capture

Guesses are dispatched fire-and-forget with `.catch()` pushing to `this.errors`, so a guess that loses a race against `close()` is captured rather than thrown as an unhandled rejection. The risk with swallowing background errors is that a real submission failure goes unnoticed; honest games guard against this by asserting `errors` stays empty on both seats, so the capture path cannot silently mask a happy-path failure. The "guess that cannot be submitted" test closes the session the instant it may guess and asserts `errors` grows.

### Labelling without touching protocol validation

`HOUSE_BOT_LABEL = 'House Bot'`, a readonly `label` (overridable per bot), and `marker()` returning `{ label, publicKey }` implement REQ-17.3 at the bot layer. The rationale is sound: the relay HELLO is fixed to `host | guest`, and the public key is already how a seat is identified in signed messages, so a room can match a badge to a seat with no change to message validation. The label/marker assertions (default, custom, and public-key pairing) are covered. The gap is only that no room UI in this diff consumes the marker — appropriate for a Node-package-scoped change, but the "labelled in the room" wording of REQ-17.3 is satisfied as a capability, not yet as a rendered badge.

### Test coverage

Covered: two honest bots to a `final` verdict with empty faults and agreed `verifiedSecrets`; default-secret and default-rng/secure-generator paths; transcript and subscription; the inconsistent-answer fallback; background-error capture on a losing race; the one-index lie caught as a `wrong-answer` fault with the honest seat winning; label and marker (default + custom); and the Session seam's honest-default and single-lie behaviour at the protocol layer.

Not tested: multiple lies in one game from the bot (only the single-index case is exercised here; the protocol suite covers multi-lie finalisation separately, so this is a scope choice rather than a gap); a cheat index that the bot never actually answers (an out-of-range or wrong-parity `atGuessIndex` would simply never fire the lie — benign, but undocumented). Neither rises to a blocking concern.

None bundled in the diff. `pnpm-lock.yaml` and the new `tsconfig.json`/`vitest.config.ts`/`package.json` are the expected scaffolding for a new workspace package. The `.agents/tasks/task-house-bot/*` JSON files are task metadata, not product code.
